### 一、 系统说明

**1. 项目概述**
本项目是一个基于 MongoDB 开发的轻量级在线问卷系统，模拟了“问卷星”和 Google Forms 的核心功能。系统支持多用户注册与隔离，允许用户创建、发布自定义问卷，配置多题型及条件跳转逻辑，并通过专属 URL 生成外发链接。所有填写数据均由系统统一收集，并自动生成结构化的统计结果。

**2. 技术栈选型**
本项目采用前后端分离的架构思路（虽然在同一服务下部署），严格遵循全量数据存储于 MongoDB 的硬性要求，未使用任何关系型数据库及现成的问卷框架。
* **后端语言**：Python
* **后端框架**：Flask（利用轻量级路由和内置 Session 进行鉴权）
* **数据库**：MongoDB（通过 `pymongo` 驱动交互，本地持久化存储）
* **前端方案**：原生 HTML/CSS 结合 **Alpine.js**（实现轻量级的响应式数据绑定和单页面应用 SPA 体验）
* **密码加密**：`bcrypt`（保障用户凭据安全）
* **测试框架**：`pytest`（用于后端 API 的自动化测试保障）

**3. 核心功能模块**
系统围绕问卷生命周期，拆解为以下四大核心模块：

* **用户权限模块**
    * 提供账号注册与加密登录功能。
    * 严格的权限隔离机制：利用装饰器（`@login_required` 和 `@survey_owner_required`）拦截越权访问，确保用户只能查看、编辑和统计自己创建的问卷。
* **问卷与题目管理模块**
    * **问卷管理**：支持自定义问卷标题、描述、过期时间，支持设置匿名填写与允许多次提交。具备“草稿”、“已发布”、“已关闭”三种状态流转。
    * **题型支持**：内置单选题、多选题、文本填空、数字填空四种基础题型。
    * **高级校验**：支持必填项设置、多选题选项数量限制、文本题字数限制以及数字题大小写及整数限制。
    * **跳转逻辑**：提供动态跳转规则设定（如：当某题选择特定选项时，直接跳至指定题目或结束问卷）。
* **问卷填写模块**
    * 前端通过全局路由标识（Slug）动态加载问卷结构，基于 Alpine.js 实现单题分页渲染。
    * 支持客户端与服务端的双重数据校验（后端采用策略模式 `QuestionValidator` 进行扩展性设计），拦截非法格式数据并给出精准提示。
* **数据统计分析模块**
    * 自动收集问卷答卷，根据不同题型采用不同的统计策略。
    * 选择题统计各选项投票数；文本题汇总所有回答记录；数字题自动计算平均值并列出所有数值。

**4. 系统架构与设计思路**
* **前后端交互**：前端通过 `api.js` 封装的 Fetch 请求调用后端的 RESTful API（如 `/api/surveys`、`/api/surveys/<slug>/submit` 等），实现数据的 JSON 格式收发。
* **无感序列化**：后端重写了 Flask 的 `DefaultJSONProvider`，全局自动处理 MongoDB 的 `ObjectId` 和 `Datetime` 对象的 JSON 序列化问题，极大地减少了数据转换的样板代码。
* **高内聚低耦合**：针对第二阶段可能发生的需求变更，后端引入了工厂/策略模式（如 `QuestionValidator`），将各个题型的校验逻辑解耦；前端采用 `<template>` 条件渲染不同视图，保证了后续增删题型或逻辑的灵活扩展性。


### 二、 数据库设计

本项目采用 MongoDB 作为底层数据存储。为了兼顾查询效率、数据扩展性以及 MongoDB 16MB 的文档大小限制，本系统没有将所有数据堆砌在一个集合中 ，而是采用了高度解耦的四集合（Collection）架构：`users`、`surveys`、`questions` 和 `answers`。

#### 4.1 核心集合 Schema 说明

**1. 用户集合 (`users`)**
用于存储用户的基本信息和关联资产。
* `_id`: ObjectId，主键。
* `username`: String，用户名。
* `password`: String，加密存储的密码。
* `created_at`: Date，注册时间。
* `email`: String，可选，预留找回密码功能。
* `created_surveys`: Array\[ObjectId]，用户创建的问卷 ID 列表（引用关系）。
* `submitted_answers`: Array\[ObjectId]，用户提交的答卷 ID 列表。

**2. 问卷集合 (`surveys`)**
存储问卷的宏观配置和状态。
* `_id`: ObjectId，主键。
* `user_id`: ObjectId，创建该问卷的用户 ID。
* `title`: String，问卷标题。
* `description`: String，问卷说明。
* `is_anonymous`: Boolean，是否允许匿名填写。
* `allow_multiple_submissions`: Boolean，是否允许多次填写。
* `status`: String，问卷状态（draft 草稿, published 已发布, closed 已关闭）。
* `expire_at`: Date，截止时间。
* `slug`: String，生成的唯一短链接标识。
* `question_count`: Number，问题总数（**冗余设计**，便于列表页快速展示，空间换时间）。
* `submission_count`: Number，收集到的答卷总数（**冗余设计**，避免每次统计都全表 count）。

**3. 题目集合 (`questions`)**
存储具体的题目细节。将题目独立成集合，便于实现复杂的动态跳转和单题修改。
* `_id`: ObjectId，主键。
* `survey_id`: ObjectId，所属问卷 ID。
* `type`: String，题型（single_choice, multiple_choice, text, number）。
* `content`: String，题目内容。
* `is_required`: Boolean，是否必答。
* `order`: Number，题目在问卷中的显示顺序。
* `options`: Array\[Object]，选择题的选项数组（包含 id, text, value）。
* **约束条件字段**（根据题型动态生效）：
    * `min_choices` / `max_choices`: 多选题的选择数量限制。
    * `min_length` / `max_length`: 文本题的字数限制。
    * `min_value` / `max_value` / `is_integer`: 数字题的范围和类型限制。
* `jumps`: Array\[Object]，**动态跳转规则设计**。将逻辑作为数据存储，避免逻辑写死在代码中。
    * `logic`: 规则间的逻辑关系（and/or）。
    * `conditions`: 触发条件数组（例如：当值为 X 时）。
    * `target_question_id`: 满足条件时跳转的目标题目 ID。

**4. 答卷集合 (`answers`)**
存储用户的实际填写数据。
* `_id`: ObjectId，主键。
* `survey_id`: ObjectId，所属问卷 ID。
* `user_id`: ObjectId，填写者 ID（若为匿名填写则为 null）。
* `created_at`: Date，提交时间。
* `responses`: Array\[Object]，具体的回答内容数组。
    * `question_id`: ObjectId，对应题目的 ID。
    * `value`: Mixed，回答的原始值（单选为字符串，多选为数组）。
    * `text`: String，针对填空题的文本记录。

#### 4.3 设计决策分析 (Design Decisions)

本节专门阐述该架构背后的设计思考，以满足项目说明中的核心技术要求。

**1. 为什么这样设计？** 
本设计采取了“主从分离”与“适度冗余”相结合的策略。
* **避免单文档膨胀**：没有将“问卷、题目、答题结果”全部塞入一个大 JSON 中。如果一份问卷收集了 10 万份答卷，内嵌设计会轻易突破 MongoDB 的 16MB 限制导致系统崩溃。将 `answers` 和 `questions` 独立建表，保证了极高的水平扩展能力。
* **谨慎使用冗余**：在 `surveys` 集合中加入了 `question_count` 和 `submission_count`。这是因为在“我的问卷”列表页，用户需要直观看到这些数据。如果每次渲染列表都要去 `questions` 和 `answers` 集合执行 `count()` 聚合操作，会造成极大的性能浪费。在插入新题目或新答卷时通过 `$inc` 原子操作维护这两个字段，是典型的“空间换时间”优化。
* **逻辑数据化**：跳转逻辑（`jumps`）被设计为 `questions` 集合中的一个数组字段。前端可以图形化配置，后端负责解析，彻底杜绝了将跳转条件写死在代码里（如 `if q1 == 'A' jump to q5`）的硬编码问题。

**2. 为什么不用关系型数据库（如 MySQL）结构？** 
关系型数据库要求高度规范化的二维表结构，这与问卷系统的需求存在天然冲突：
* **属性稀疏问题**：在本系统中，不同题型拥有完全不同的限制属性。文本题有 `max_length` ，多选题有 `max_choices` ，数字题有 `is_integer`。如果使用关系型数据库，要么需要建一张包含所有可能属性的“宽表”（会导致大量 `NULL` 值，浪费空间），要么需要使用极其复杂的 EAV（Entity-Attribute-Value）反模式建表，这将导致查询 SQL 异常复杂且性能低下。
* **层级数据的拆解**：选择题的 `options`（选项） 和题目的 `jumps`（跳转规则）  在关系型数据库中都需要单独建立一对多关联表（如 `question_options` 表、`question_jumps` 表）。这会导致在查询一道完整的题目时，需要执行多次 `JOIN` 操作。

**3. 为什么这种结构特别适合 MongoDB？** 
* **Schema-Free（无模式）的优势**：MongoDB 的文档模型完美契合了“异构数据”的存储需求。在 `questions` 集合中，单选题的文档可以只有 `options` 字段，而数字题的文档可以只有 `max_value` 字段，两者互不干扰，自然存储，无需预先修改表结构。
* **内嵌数组的强力支持**：MongoDB 极擅长处理具有强生命周期绑定的子属性。题目选项（`options`）和跳转规则（`jumps`）脱离了题目本身毫无意义。在 MongoDB 中，我们可以直接将它们作为 Array 嵌套在 `questions` 文档内部。一次简单的 `find()` 查询就能取出题目的所有相关信息，读取性能极高，也大大简化了后端处理逻辑。同时，这也为第二阶段应对需求变更（如新增题型或新属性）留下了极大的弹性空间。
### 三、 API 说明

本项目后端采用 RESTful API 设计风格，所有接口均通过 JSON 格式进行数据交换。除问卷填写相关接口外，大部分接口要求用户处于登录状态。

#### 1. 通用说明
* **Base URL**: `/api`
* **Content-Type**: `application/json`
* **认证方式**: 基于 Flask Session 的 Cookie 认证。执行登录后，后续请求需携带 Session Cookie。

---

#### 2. 用户认证 API
用于处理用户的注册、登录、登出及身份检查。

* **用户注册**
    * **URL**: `POST /api/register`
    * **请求体**: `{ "username": "...", "password": "...", "email": "..." }`
    * **功能**: 创建新用户，密码经过 bcrypt 加密存储。

* **用户登录**
    * **URL**: `POST /api/login`
    * **请求体**: `{ "username": "...", "password": "..." }`
    * **响应**: 返回登录成功的用户信息，并在 Cookie 中设置 Session。

* **获取当前用户信息**
    * **URL**: `GET /api/me`
    * **功能**: 检查当前登录状态，返回当前用户的 ID 和用户名。

---

#### 3. 问卷管理 API (需登录)
此类接口受 `@survey_owner_required` 装饰器保护，确保用户只能操作自己创建的问卷。

* **获取问卷列表**
    * **URL**: `GET /api/my_surveys`
    * **功能**: 返回当前登录用户创建的所有问卷列表。

* **创建问卷**
    * **URL**: `POST /api/surveys`
    * **请求体**: `{ "title": "...", "description": "...", "is_anonymous": true/false, "expire_at": "ISO-Date" }`
    * **功能**: 初始化问卷基本信息，生成唯一的 `slug` 用于分发。

* **添加题目**
    * **URL**: `POST /api/surveys/<survey_id>/questions`
    * **请求体**: 包含题目类型（`single_choice`, `multiple_choice`, `text`, `number`）、内容、选项及校验规则（如 `min_length`, `max_value` 等）。

* **更新题目（含跳转逻辑）**
    * **URL**: `PUT /api/questions/<question_id>`
    * **功能**: 修改题目内容或设置跳转规则。跳转逻辑存储于 `jumps` 数组中，定义了满足特定条件时跳转的目标题目 ID。

* **发布/关闭问卷**
    * **URL**: `POST /api/surveys/<survey_id>/publish` 或 `/api/surveys/<survey_id>/close`
    * **功能**: 修改问卷状态。只有“已发布”状态的问卷才允许外部填写。

---

#### 4. 问卷填写与提交 API
此类接口支持匿名访问或根据问卷设置要求登录访问。

* **获取填写页问卷数据**
    * **URL**: `GET /api/fill_survey/<slug>`
    * **功能**: 根据 URL 中的 Slug 获取问卷标题、描述及完整的题目列表。会检查问卷是否过期或关闭。

* **提交问卷答案**
    * **URL**: `POST /api/surveys/<slug>/submit`
    * **请求体**: `{ "responses": [ { "question_id": "...", "value": "...", "text": "..." }, ... ] }`
    * **功能**: 后端 `QuestionValidator` 会逐题校验答案合法性，校验通过后将答卷存入 `answers` 集合。

---

#### 5. 统计分析 API (需登录)
* **获取问卷统计结果**
    * **URL**: `GET /api/surveys/<survey_id>/statistics`
    * **功能**: 实时聚合 `answers` 集合中的数据。
        * **选择题**: 计算各选项的得票数。
        * **文本题**: 罗列所有填写的文本内容。
        * **数字题**: 计算平均值并返回所有原始数值。

### 四、 关键逻辑说明

系统的核心业务逻辑主要集中在数据校验、跳转控制、权限隔离以及数据统计四个方面。为了兼顾代码的健壮性与第二阶段的可扩展性，本系统在逻辑实现上采用了诸多设计模式与优化手段。

#### 5.1 数据校验逻辑（策略模式与双端校验）
为保证收集到的数据绝对合法，系统实现了前端拦截与后端兜底的**双端校验**机制。

* **前端即时校验**：在 `app.js` 的 `validateAndSaveCurrentAnswer` 方法中，用户点击“下一题”时，前端会立刻根据题目属性（如 `is_required`、`min_length`、`max_value` 等）进行校验。如果不合规，直接弹窗拦截，提升用户体验，减少无效的网络请求。
* **后端策略模式校验（核心扩展点）**：恶意用户可能绕过前端直接发送 API 请求，因此后端校验不可或缺。在 `app.py` 中，独立封装了 `QuestionValidator` 策略类。
    * **动态路由**：校验主方法 `validate()` 会根据题目的 `type` 字段，利用 Python 的反射机制（`getattr`）自动动态调用对应的私有校验方法（如 `_validate_multiple_choice`）。
    * **为二阶段铺垫**：这种设计彻底消除了臃肿的 `if-else` 逻辑。在第二阶段如果需求变更（例如新增一种“矩阵打分题”），核心路由代码完全不需要修改，只需在 `QuestionValidator` 中新增一个 `_validate_matrix` 方法即可，完美符合“开闭原则”。

#### 5.2 条件跳转逻辑（数据驱动设计）
为了满足“不把跳转写死在程序里”的需求，系统将跳转逻辑彻底**数据化**。

* **存储结构**：在 MongoDB 的 `questions` 集合中，每道题都有一个 `jumps` 数组。它记录了“逻辑条件（equals/contains）”、“目标值”以及“目标题目 ID（`target_question_id`）”。
* **执行引擎**：跳转的实际执行放在了前端（`app.js` 的 `goToNextQuestion` 方法）。当用户答完当前题，程序会遍历该题的 `jumps` 数组，比对用户的真实回答与预设的 `value`。
    * 如果匹配成功，且目标 ID 为 `null`，则直接触发问卷结束逻辑。
    * 如果匹配成功且有目标 ID，前端会在题目列表中查找该目标题目的索引（Index），直接将渲染指针（`currentQuestionIndex`）切过去。
    * 如果没有匹配到任何规则，则按物理顺序进入下一题。

#### 5.3 权限与访问控制逻辑（装饰器拦截）
系统后端利用 Flask 的特性，构建了两道安全防线，保证数据不被越权篡改：

* **第一道防线（身份认证）**：`@login_required` 装饰器拦截所有需要登录的 API，检查 Session 中是否存在 `user_id`，防止未登录访问。
* **第二道防线（资源鉴权）**：`@survey_owner_required` 装饰器用于修改、发布、统计问卷的敏感接口。在执行具体视图函数前，它会先去 MongoDB 查询目标问卷，比对问卷的 `user_id` 与当前 Session 的 `user_id`。如果不一致，直接返回 403 错误并记录安全日志（`logger.warning`）。更巧妙的是，它会将查询到的 `survey` 对象作为参数直接传递给下层函数，避免了数据库的重复查询。

#### 5.4 序列化优化逻辑（JSON Provider 覆写）
这是后端代码中一处显著的性能与代码整洁度优化点。

* **痛点**：MongoDB 的 `ObjectId` 类型和 Python 的 `datetime` 类型无法被原生的 JSON 库直接序列化，通常需要在每个 API 返回前手动写循环（如 `str(item['_id'])`）进行转换，产生大量样板代码。
* **解决方案**：系统在初始化时自定义了 `MongoJSONProvider`，继承并覆写了 Flask 的默认 JSON 编码器。在这个底层拦截器中，统一识别并转换这两种特殊格式。这使得在所有的路由函数中，我们可以直接写 `return jsonify(data)`，极大地提高了代码的清爽度和开发效率。

#### 5.5 统计与聚合逻辑
在获取问卷统计结果时（`get_statistics`），系统采取了按题型分类聚合的逻辑：
* 后端一次性拉取该问卷的所有题目和所有答卷。
* 通过遍历答卷数据，针对单选/多选题，利用字典（Dictionary）进行票数累加计算；针对文本题，将内容追加到列表中；针对数字题，不但记录所有的原始输入，还会自动计算算术平均值。
* 统计结果以题目 ID 为键组装成结构化的 JSON 返回前端渲染，确保图表展示的数据实时、准确。
