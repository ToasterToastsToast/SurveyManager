# 项目完成报告

repo:`https://github.com/ToasterToastsToast/SurveyManager`

## 一、 项目目标
本项目第一阶段的目标是设计并开发一个简化版的在线问卷系统，核心功能对标“问卷星”与 Google Forms 。通过本项目的实操，旨在锻炼和综合考核以下几个核心能力：
1. **系统设计与全栈开发能力**：基于前后端分离的思想构建系统，实现从用户注册登录、问卷创建分发、表单填写到数据统计的完整业务闭环 。
2. **MongoDB 数据库设计能力**：摒弃传统关系型数据库思维，利用文档型数据库的特性进行业务逻辑与数据结构的建模 。
3. **复杂逻辑的实现能力**：重点攻克问卷系统中不同题型的条件校验逻辑以及基于用户选项的动态跳转逻辑 。
4. **AI 辅助编程实践**：规范并高效地使用 AI 工具提升开发效率，同时保持对核心代码的架构掌控力 。
此外，第一阶段的系统架构需要保持高度的扩展性与解耦性，为第二阶段不可预知的“需求变更”打下坚实的基础，确保未来在不抛弃现有成果的前提下平滑迭代 。

---

## 二、 系统设计
本项目采用轻量级的技术栈组合：
* **后端**：使用 Python + Flask 框架。利用 Flask 轻量级的路由机制提供 RESTful API 。
* **数据库**：MongoDB（通过 `pymongo` 驱动交互）。所有核心数据均严格存储在 MongoDB 中 。
* **前端**：遵循“不要求复杂界面”的原则，采用原生 HTML/CSS 配合 Alpine.js 构建 。Alpine.js 提供了类似 Vue 的响应式数据绑定体验，完美实现了无需脚手架的单页面应用（SPA）交互。
* **架构亮点**：为了彻底解决 MongoDB 中 `ObjectId` 和 `Datetime` 对象无法直接被 JSON 序列化的问题，后端重写了 Flask 的 `DefaultJSONProvider`，实现了底层无感转换，极大地清爽了业务路由层的代码。

---

## 三、 MongoDB 设计
系统采用了“主从分离”与“适度冗余”相结合的四集合（Collection）架构：`users`、`surveys`、`questions` 和 `answers` 。

* **为什么这样设计？**
  坚决避免将“问卷配置、所有题目、所有答卷”嵌套在同一个庞大文档中 。
  如果一份问卷收集了海量答卷，内嵌设计极易突破 MongoDB 的 16MB 限制导致系统崩溃。拆分 `questions` 和 `answers` 保证了系统极高的水平扩展能力。同时，在 `surveys` 中保留了 `question_count` 和 `submission_count` 进行适度冗余，避免了列表页高频的 `count()` 聚合查询 。
* **为什么不用关系型数据库结构？**
  问卷题目具有典型的“属性稀疏”特征。文本题有字数限制，数字题有大小限制。关系型数据库若要兼容，要么建含有大量 NULL 的宽表，要么使用复杂的 EAV 模型 。
* **为什么适合 MongoDB？**
  MongoDB Schema-Free 的特性完美契合异构题型数据 。并且，题目的选项（`options`）和跳转规则（`jumps`）可以直接作为内嵌数组（Array）存储在 `questions` 文档中，一次查询即可获取完整题目结构，免去了关系型数据库中繁琐的多表 JOIN 操作。

## 四、 跳转设计
为了满足“跳转逻辑不能写死在代码里”的硬性要求，本系统采用了**数据驱动的动态跳转设计** 。
1. **数据存储**：跳转规则被抽象为一个 `jumps` 数组，作为子属性存在 `questions` 集合的对应题目文档中。内部定义了触发条件（如 `equals: '1'`）和目标题目 ID（`target_question_id`）。
2. **前端引擎**：答题时的跳转计算引擎放在了前端（`app.js`）。当用户作答完毕点击“下一题”时，前端逻辑会比对用户的真实答案与当前题目的 `jumps` 规则。若命中规则，且目标为 `null`，则直接触发问卷结束标记；若有目标 ID，则将渲染指针（Index）直接拨至目标题目，跳过中间无关题目。

---

## 五、 校验设计
为保障数据质量，防范恶意提交，系统采用了**前端拦截与后端策略模式双重校验**。
1. **前端即时校验**：用户交互时，根据题目设定的 `is_required`、`min_length`、`min_choices` 等属性实时预判，不合法则弹窗拦截。
2. **后端策略校验（核心）**：为了应对第二阶段可能的题型扩展，后端设计了 `QuestionValidator` 校验策略类。系统根据传入答卷的 `type` 字段，利用反射机制自动路由至私有的子校验方法（如 `_validate_number`）。这种设计消除了冗长的 `if-else`，如果未来增加新题型，只需在验证器中增加对应方法即可，原有的核心接口代码完全无需改动。

## 六、 AI 使用过程
在本项目开发中，我没有将 AI 视为简单的“一键代码生成器”，而是采用了**多模型对抗（Gemini Pro 与 IDE 内置 Agent 交叉比对）**和**严格的 Code Review（代码审查）**策略。整个过程中，由我主导业务需求与系统架构，AI 负责基础代码的落地与测试脚本的编写。

**1. AI 做了什么（提供基础建设与提效）：**
* **骨架搭建**：AI 协助我快速构建了基于 Flask + PyMongo 的后端 RESTful API 基础框架。在前端，根据我“绝对禁止引入繁重构建工具”的严格约束，AI 成功输出了基于 Alpine.js 和原生 ES6 Module 的无构建单页应用（SPA）代码。
* **自动化与测试赋能**：AI 为我编写了基于 `pytest` 的接口打流自动化测试脚本，以及用于极限压力测试的 `seed_mega.py` 海量数据播种脚本，极大节省了手动造数据的时间。

**2. AI 做错了什么（逻辑盲区与工程缺陷）：**
* **架构视野局限**：初期生成的 MongoDB Schema 缺乏冗余设计，问卷跳转规则过于扁平化，且完全遗漏了问卷的生命周期管理（关闭/过期机制）。
* **API 废弃与跨平台兼容差**：AI 错误使用了 PyMongo 已废弃的 `.count()` 方法；在提供一键修复脚本时，忽略了 Windows PowerShell 默认的 GBK 编码，导致项目文件中文乱码崩溃。
* **前后端数据契约脱节**：AI 编写的测试脚本与后端逻辑出现字段定义冲突（如 `"text"` 与 `"value"` 的错位），导致测试用例大面积误报失败。

**3. 我改了什么（主导重构与纠错）：**
* 我通过多窗口 prompt 对抗，迫使 AI 放弃简单的表结构，迭代出了包含 `Mixed` 类型、灵活的 `jumps` 数组以及无冗余聚合计算的完善数据库模型。
* 在第二阶段应对需求扩展时，我主动要求 AI 放弃原有的“面条式（Spaghetti code）”堆砌，采用“策略模式”和自定义 JSON 编码器进行深度重构，将系统从跑通拉升到了高可维护的工程标准。

## 七、 测试结果

为了验证系统的健壮性，我结合 AI 生成的脚本进行了多维度测试，并在测试中不断闭环修复问题：

1. **自动化 API 单元测试**：运行 `test_api.py`，覆盖了注册登录、问卷创建、权限拦截等核心链路。修复了前后端字段不一致导致的网络熔断问题，最终测试用例全部 `PASSED`。
2. **异常边界测试（Negative Testing）**：通过脚本故意注入非法数据（如必填项为空、数字题越界、多选题选超上限），验证了后端可以正确拦截并返回 400 状态码，前后端数据动态校验闭环完整。
3. **极限压力与性能测试**：使用定制的 `seed_mega.py` 脚本，瞬间注入了 1 份包含 50 道复杂题型（涵盖网状跳转）的超大问卷及 500 份并发模拟答卷。
   * *测试暴露问题*：500 份长文本答案直接撑爆了前端页面布局导致卡死。
   * *修复结果*：追加了 CSS `word-break: break-all` 强制换行属性，并设定 `max-height` 配合原生滚动条，成功消化了海量数据渲染。
4. **手动测试**: 人工模拟操作进行对前端的检验。
   *  暴露问题与结果：见AI对话日志。

## 八、 遇到的工程问题与解决记录

在实际开发与调试中，我遇到了大量由于 AI 考虑不严谨以及系统复杂度上升带来的工程化问题。以下是核心排查与修复过程：

### 问题 1：前端“幽灵白屏”与异常拦截冲突
* **现象与影响**：页面无法交互，彻底白屏。
* **AI 的失误与技术根因**：AI 在前端 HTML 中写错了静态资源的相对路径（引发 404）。更致命的是，AI 在后端编写了一个极其粗暴的全局异常捕获器（`@app.errorhandler(Exception)`），将正常的静态文件 404 错误统一转化为了 500 JSON 报错。这导致浏览器预期接收 JS 文件却收到了 JSON 报错，进而渲染引擎崩溃。
* **我的修复**：我通过浏览器 F12 的 Network 面板精准定位了 404 到 500 的异常转化。随后修改了后端拦截器，引入 `HTTPException` 放行了标准 HTTP 错误，并手动修正了 HTML 中的所有路径。

### 问题 2：Alpine.js 渲染崩溃与生命周期错乱
* **现象与影响**：组件加载失败，点击“下一题”触发跳转结束时页面突然变白。
* **AI 的失误与技术根因**：
  1. 违反了 Alpine.js 的底层规范，在 `<template x-if>` 内部放置了多个平级的根节点。
  2. 插值语法错误：在 HTML 中使用了未加引号的中文字符串（如 `x-text="第 + q.order + 题"`），引发 JavaScript `ReferenceError`。
  3. 遗漏了跳出逻辑的兜底 UI，导致数组越界。
* **我的修复**：我梳理了 DOM 结构，使用唯一的 `<div>` 根节点包裹模板；将中文字符转换为标准的 JS 字符串拼接；并自主设计补充了“答题结束/准备提交”的平滑过渡页面，彻底解决了跳题白屏问题。

### 问题 3：历史脏数据导致后端 500 崩溃 (`KeyError`)
* **现象与影响**：第二阶段提交旧版本问卷时，服务器直接抛出 500 内部错误。
* **AI 的失误与技术根因**：在二阶段增加 `allow_multiple_submissions` 等控制字段后，AI 的校验代码直接使用了 `survey['allow_multiple_submissions']` 进行字典强制取值。它没有考虑数据库中仍存有第一阶段创建的、没有该字段的“历史脏数据”，导致读取触发 `KeyError`。
* **我的修复**：引入了向后兼容的“防御性编程”思想。将直接取值修改为安全的 `.get('allow_multiple_submissions', False)`，即使字段缺失也能赋予默认值，并在题目创建接口增加了对“无选项选择题”的源头拦截，增强了系统鲁棒性。

### 问题 4：前后端数据契约不一致与 ObjectId 解析异常
* **现象与影响**：自动化测试填空题全部失败；前端点击“查看统计”报错 `InvalidId`。
* **AI 的失误与技术根因**：
  1. AI 的测试脚本给后端发送的填空答案键名为 `"text"`，而后端校验逻辑却在读取 `"value"`。
  2. 前端“查看统计”按钮绑定的 `@click="viewStats()"` 忘记传入当前问卷 ID，导致后端收到字符串 `'null'` 并抛出解析异常。
* **我的修复**：统一了前后端对填空题的值键名契约；追踪 JS 的状态变量流转，将 `survey._id` 正确传导进点击事件，打通了统计数据链路。

### 问题 5：后端架构耦合与二阶段重构
* **现象与影响**：随着题目类型和业务逻辑的增加，`app.py` 中的 `submit_survey` 充斥着庞大的 `if-elif` 校验块，代码可读性和扩展性极差，难以应对第二阶段的需求变更。此外，代码中到处散落着将 ObjectId 和 datetime 序列化为字符串的样板代码。
* **我的修复（深度重构）**：
  1. **消灭样板代码**：引入自定义 `DefaultJSONProvider`，全局自动处理 ObjectId 序列化，精简了大量字典遍历代码。
  2. **化解 if-else 地狱**：引入“策略模式（Strategy Pattern）”，抽象出独立的 `QuestionValidator` 类。通过反射机制处理不同题型的多态校验，使得新增题型不再需要修改核心路由，完全符合“开闭原则”。
  3. **解耦鉴权逻辑**：将权限判断提炼为 `@login_required` 和 `@survey_owner_required` 装饰器，实现了面向切面（AOP）的权限控制。
