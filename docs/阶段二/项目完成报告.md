# 项目完成报告

repo:`https://github.com/ToasterToastsToast/SurveyManager`

## 一、 项目目标
本项目第二阶段的目标是对现有问卷系统进行大规模更新，核心功能围绕“题目管理”展开，实现题目复用、共享、版本控制等高级特性。通过本阶段的开发，旨在：
1. **增强题目管理能力**：实现题目独立存在、复用、共享和版本控制，解决用户重复创建题目的痛点。
2. **提升系统可靠性**：通过版本隔离机制，确保修改题目不会影响已发布问卷，保证数据一致性。
3. **优化用户体验**：建立题库管理系统，方便用户整理和使用常用题目。
4. **扩展统计分析能力**：实现跨问卷的题目统计，为用户提供更全面的数据洞察。
5. **保持系统可扩展性**：在现有架构基础上进行扩展，确保系统能够应对未来的需求变更。

---

## 二、 系统设计
本项目在第一阶段的基础上进行了大规模扩展，保持了原有的技术栈，同时增加了新的功能模块：
* **后端**：继续使用 Python + Flask 框架，扩展了 RESTful API 以支持题目管理、版本控制、题库管理等新功能。
* **数据库**：MongoDB（通过 `pymongo` 驱动交互），按照 v2schema 对数据结构进行了重构。
* **前端**：在原有基础上扩展，增加了题目管理、题库管理、版本历史查看等新界面和交互逻辑。
* **架构亮点**：
  1. **题目与问卷解耦**：题目成为独立的实体，通过 `base_question_id` 关联同一题目的不同版本，实现了题目生命周期与问卷的分离。
  2. **版本控制机制**：实现了题目版本的创建、追踪和恢复，确保历史问卷不被污染，保证数据一致性。
  3. **权限管理增强**：支持题目和题库的共享，实现了基于用户的细粒度权限控制。
  4. **跨问卷统计**：基于 `base_question_id` 实现了同一题目在多个问卷中的数据汇总，为用户提供更全面的数据洞察。
  5. **写时复制机制**：引入了题目修改的“写时复制”机制，确保版本链条的完整与准确，防止历史版本丢失。

## 三、 MongoDB 设计
系统在第一阶段的基础上，对数据结构进行了重大重构，引入了新的集合和字段，实现了题目管理的核心功能：

### 1. 题目集合 (`questions`) - 核心创新
* **核心变更**：
  - 新增 `base_question_id`：同一题目的所有版本共享此ID，用于跨问卷统计，是实现跨问卷统计的关键。
  - 新增 `version`：版本号，用于追踪题目演进，确保版本管理的清晰性。
  - 新增 `previous_version_id`：上一版本ID，用于追溯修改历史，实现版本链条的完整性。
  - 新增 `owner_id`：题目创建者，用于权限控制，确保数据安全。
  - 新增共享与状态管理字段：`is_public`、`shared_with_users`、`used_in_surveys`，实现题目共享和使用追踪。
  - 移除 `is_required`、`order`、`jumps` 字段：这些是“问卷上下文属性”，移至 Survey 表，实现了题目内容与问卷上下文的解耦。

### 2. 问卷集合 (`surveys`) - 结构优化
* **核心变更**：
  - 新增 `questions` 数组：维护问卷包含的题目及上下文属性，每个元素包含 `question_id`、`order`、`is_required`、`jumps`，实现了题目上下文的独立管理。

### 3. 题库集合 (`question_banks`) - 全新集合
* **新增集合**：
  - 包含 `name`、`description`、`owner_id`、`is_public`、`shared_with_users`、`questions` 等字段。
  - `questions` 字段存储 `base_question_id` 列表，永远指向该题目的最新版本，实现了题库与题目版本的动态关联。

### 4. 回答集合 (`answers`) - 统计增强
* **核心变更**：
  - 新增 `base_question_id`：题目的基础ID，用于跨问卷统计，确保统计数据的准确性。

### 5. 用户集合 (`users`) - 权限扩展
* **核心变更**：
  - 新增 `question_banks` 字段：用户拥有或加入的题库ID列表，实现了用户与题库的关联。

### 设计优势
1. **版本隔离**：通过独立的题目版本文档，确保修改题目不会影响已发布问卷，保证数据一致性。
2. **高效统计**：基于 `base_question_id` 的跨问卷统计，避免了复杂的聚合查询，提高了统计效率。
3. **权限控制**：细粒度的共享机制，支持题目和题库的公开和定向共享，确保数据安全。
4. **扩展性**：预留了 `metadata` 字段，为未来功能扩展做准备，保持系统的可扩展性。
5. **数据一致性**：通过 `base_question_id` 和 `previous_version_id` 建立了完整的版本链条，确保数据的一致性和可追溯性。

## 四、 跳转设计
保持了第一阶段的数据驱动动态跳转设计，同时进行了优化：
1. **数据存储**：跳转规则仍然存储在 `surveys` 集合的 `questions` 数组中，作为每个题目的上下文属性，实现了跳转逻辑与题目内容的分离。
2. **前端引擎**：答题时的跳转计算引擎保持不变，在前端（`app.js`）实现，确保了跳转逻辑的灵活性。
3. **兼容性**：确保了与第一阶段跳转逻辑的向后兼容，同时支持新版本的题目结构，保证了系统的稳定性。

## 五、 校验设计
在第一阶段的基础上，扩展了校验逻辑，实现了更全面的验证机制：
1. **前端即时校验**：保持了原有的前端校验逻辑，同时适配了新的题目结构，确保用户输入的合法性。
2. **后端策略校验**：扩展了 `QuestionValidator` 校验策略类，支持新的题目字段和版本控制逻辑，确保数据的一致性。
3. **权限校验**：新增了题目和题库的权限校验，确保用户只能访问和修改有权限的资源，保证数据安全。
4. **版本校验**：实现了对已发布问卷中题目修改的拦截，防止历史问卷被污染，保证数据的一致性。
5. **上下文校验**：区分了题目内容修改和问卷上下文修改，确保不同类型的修改采用不同的处理策略。

## 八、 遇到的工程问题与解决记录

在第二阶段的开发与调试中，我遇到了大量由于系统复杂度上升带来的工程化问题。以下是核心排查与修复过程：

### 问题 1：前端白屏与 404 错误
* **现象与影响**：浏览器访问 http://127.0.0.1:5000/ 时出现白屏，控制台显示 404 错误，用户无法访问系统。
* **技术根因**：Flask 未配置根路径与静态文件路由，导致前端资源无法加载。
* **解决方案**：在 app.py 中添加根路径返回 index.html、静态文件访问路由及用户登录状态 API，解决白屏 404 问题，确保用户可以正常访问系统。

### 问题 2：版本管理逻辑错误
* **现象与影响**：修改题目后历史版本丢失，恢复旧版本时服务器内部错误，导致版本链条断裂。
* **技术根因**：版本号计算错误、未更新问卷题目引用、返回语句缺失，未能正确实现“写时复制”机制。
* **解决方案**：修复后端代码中版本号逻辑、补充问卷引用更新逻辑并修正返回语句，引入“写时复制”机制确保版本链条完整，保证了版本管理的正确性。

### 问题 3：权限控制不完整
* **现象与影响**：共享用户无法复用题库题目到问卷中，权限控制存在漏洞。
* **技术根因**：复用接口权限检查遗漏，未考虑题库层权限，权限校验点不全面。
* **解决方案**：补充“题库层权限”判断，将权限控制从单对象扩展到资源所属容器（题库）层级，完善了权限控制体系，确保了数据安全。

### 问题 4：前端交互问题
* **现象与影响**：填写问卷按钮无反应，刷新页面时错误弹出填写 slug 窗口，用户体验不佳。
* **技术根因**：前端状态变量与模态框机制缺失，初始化逻辑问题，状态管理混乱。
* **解决方案**：改用统一的状态控制+模态框方案，重构初始化逻辑，引入 URL 驱动状态恢复机制，解决了前端交互问题，提升了用户体验。

### 问题 5：数据模型不一致
* **现象与影响**：题库“另存为新题”后旧版本丢失，历史版本显示混乱，数据结构不清晰。
* **技术根因**：`base_question_id` 重复导致版本覆盖，“覆盖旧题”时数据仅存入数组而未生成独立文档，数据模型设计不一致。
* **解决方案**：重新设计题目的“写时复制”机制，通过在更新前强制创建历史快照，确保版本链条的完整与准确，保证了数据模型的一致性。

### 问题 6：接口语义泛化
* **现象与影响**：更新题目时报缺少 survey_id，无法支持题库场景。
* **技术根因**：后端接口强依赖 survey_id，接口语义过于狭窄，无法适应不同场景。
* **解决方案**：重构接口以支持题库场景分支，提升接口复用能力，解决了接口强依赖 survey_id 的问题，增强了接口的灵活性。

### 问题 7：版本链数据不完整统计
* **现象与影响**：题目使用情况只显示最后一个问卷，统计数据不完整。
* **技术根因**：统计逻辑未聚合所有版本的使用记录，只考虑了当前版本。
* **解决方案**：改为聚合所有版本的使用记录，确保使用情况统计完整，为用户提供了准确的使用情况信息。

### 问题 8：新题错误加入问卷
* **现象与影响**：创建新版本题目时，新题错误地加入了问卷，数据隔离失败。
* **技术根因**：字段继承问题（survey_id 污染），新题创建时未正确清除上下文信息。
* **解决方案**：修复新题创建逻辑，确保数据隔离，防止新题错误加入问卷，保证了数据的正确性。

通过以上问题的排查与修复，系统的稳定性和可靠性得到了显著提升，所有功能均已按照需求变更的要求实现。阶段二的开发不仅实现了题目管理的核心功能，还通过技术创新和架构优化，提升了系统的整体质量和用户体验。
